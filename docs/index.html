Quick Start

Get ScriptManager running in 5 minutes.

Prerequisites

  • Python 3.10 or later
  • (Optional) Redis — only required for distributed mode. Use Memurai on Windows or Docker: docker run -d -p 6379:6379 redis:7
  • (Optional) NSSM for Windows service features — nssm.cc
⚡
One-click install (workstation): from a PowerShell prompt run .\bootstrap.ps1 — it creates a venv, installs the package (inproc mode, no Redis), and initializes the DB. Skip to step 4 below.
  1. Create a virtual environment & install
    cd d:\repos\Test
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# Workstation (in-process) — the default. No Redis, no Celery.
pip install -e ".[dev]"

# OR distributed mode (multi-host, requires Redis):
# pip install -e ".[dev,celery]"
  2. Configure
    Copy-Item .env.example .env
notepad .env

    Defaults work out of the box for workstation use (SQLite, port 8765, inproc executor). Set SCRIPTMGR_EXECUTOR_MODE=celery only if you want distributed workers.

  3. Initialise the database
    scriptmgr db init

    Creates data\scriptmgr.db with all tables.

  4. Start the server
    # Workstation / inproc mode — single command, no separate worker needed
scriptmgr serve

# Distributed / celery mode — also start a worker in a second terminal
# scriptmgr worker

    Dashboard: http://localhost:8765  |  API docs: http://localhost:8765/api/docs

  5. Register a group and script, then run it
    scriptmgr group add "AI Workflows" -d "My AI pipeline scripts"
scriptmgr script add .\samples\hello.py --group 1 --name hello
scriptmgr script run hello --watch
  6. Schedule it (every hour)
    scriptmgr schedule add --type cron --expr "0 * * * *" --script 1
✅

That's it! The dashboard at http://localhost:8765 shows live run status, logs, and history for all your scripts.

ScriptManager ships with two interchangeable executor backends. Choose with SCRIPTMGR_EXECUTOR_MODE in your .env:

inproc (default)celery
Best forSingle workstation / dev boxMultiple hosts / heavy parallel load
DependenciesPython onlyPython + Redis (or Memurai)
Worker processNone — runs inside API server via a thread poolSeparate scriptmgr worker process(es)
Log streamingIn-process pub/subRedis pub/sub
Install extranonepip install -e ".[celery]"

Both modes use the same DB, same API, same UI — you can switch by changing one env var.

Groups & Scripts

Organise scripts into nested folders.

Groups

Groups are folders that organise your scripts. They can be nested (parent → child). Examples: AI/Preprocessing, Reports/Daily, Ops/Monitoring.

# Create a top-level group
scriptmgr group add "AI Workflows" -d "All AI pipeline scripts"

# Create a nested group
scriptmgr group add "AI/Preprocessing" --parent 1

# List all groups
scriptmgr group list

Scripts

A script registration stores the path to your .py file plus metadata: interpreter, virtual-env, arguments, environment variables, timeout, and tags.

# Register a script
scriptmgr script add .\pipelines\fetch_data.py \
    --group 1 \
    --name fetch-data \
    --interpreter python \
    --venv .\venvs\pipeline-venv \
    --timeout 300 \
    --tags "data,ai,daily" \
    -d "Fetches raw data from API"

# List scripts (optionally filtered by group)
scriptmgr script list --group 1

# Update a script
#  (use PATCH /api/scripts/{id} via the API or re-add)

# Delete
scriptmgr script delete 3

Script Fields Reference

FieldDefaultDescription
path—Path to the .py file (absolute or relative)
interpreterpythonPython executable path (e.g. python3.11)
venv""Path to a virtualenv — if set, uses its Python automatically
args[]Extra CLI arguments passed to the script
env{}Extra environment variables (dict) merged with the process env
cwdscript directoryWorking directory for the process

💡

Virtualenv resolution: If venv is set, ScriptManager automatically uses {venv}\Scripts\python.exe on Windows (or {venv}/bin/python on Linux) regardless of what interpreter says.

Run Modes

Four ways to execute your scripts.

🎯 One-Shot (Manual)

Trigger a script immediately — from the dashboard, CLI, or API. Runs once and stops.

scriptmgr script run my-script --watch

🕐 Scheduled Batch

Run on a cron schedule, fixed interval, or specific date. Each fire creates one run.

# Cron: every day at 2am
scriptmgr schedule add --type cron \
  --expr "0 2 * * *" --script 1

# Every 10 minutes
scriptmgr schedule add --type interval \
  --expr "600" --script 2

# Once at a specific time
scriptmgr schedule add --type date \
  --expr "2026-06-01T09:00:00" --script 3

🔁 Continuous Re-Run

When the script finishes, automatically re-queue it after a delay. Runs forever until you disable the schedule.

# Restart 10s after completion
scriptmgr schedule add --type continuous \
  --expr "10" --rerun-delay 10 --script 4

♾ Always-On Service

Wrap the script as a Windows service (NSSM). It starts on boot, auto-restarts on crash, and sends heartbeats to the dashboard.

scriptmgr always-on install my-watcher \
  --script .\watchers\watcher.py \
  --heartbeat 30

Cancelling a Run

scriptmgr run cancel 42
# or via API:
# POST /api/runs/42/cancel
⚠️

Cancel marks the DB record as cancelled immediately. The underlying subprocess may still be running briefly until the worker notices. For hard kills, use the timeout_sec field or NSSM service controls.

DAG Workflows

Chain scripts together with conditional logic, parallel execution, and retries.

DAG Structure

A workflow is a JSON document with nodes (script references) and edges (connections with conditions).

FieldDescription
nodes[].idUnique node ID within this workflow (string)
nodes[].script_idID of the registered script to run
nodes[].retryNumber of retries on failure (default 0)
nodes[].timeout_secNode-level timeout override (0 = use script default)
nodes[].labelHuman-readable label for diagrams
edges[].fromSource node ID
edges[].toTarget node ID
edges[].on"success" | "failure" | "always"

Example: AI Pipeline

📥 fetch
──success──▶
⚙ process
──success──▶
📄 report
process ──failure──▶
🔔 notify
report ──always──▶
🔔 notify
&
🧹 cleanup
// samples/sample_workflow.json
{
  "nodes": [
    {"id": "fetch",   "script_id": 1, "label": "Fetch data",     "retry": 1},
    {"id": "process", "script_id": 2, "label": "Process data"},
    {"id": "report",  "script_id": 3, "label": "Generate report"},
    {"id": "notify",  "script_id": 4, "label": "Send notification", "retry": 2},
    {"id": "cleanup", "script_id": 5, "label": "Cleanup temp files"}
  ],
  "edges": [
    {"from": "fetch",   "to": "process", "on": "success"},
    {"from": "process", "to": "report",  "on": "success"},
    {"from": "process", "to": "notify",  "on": "failure"},
    {"from": "report",  "to": "notify",  "on": "always"},
    {"from": "report",  "to": "cleanup", "on": "success"}
  ]
}

Register & Run a Workflow

# Register from a JSON file
scriptmgr workflow add .\samples\sample_workflow.json \
    --group 1 --name "AI Pipeline"

# Run immediately
scriptmgr workflow run 1

# List workflows
scriptmgr workflow list

# Schedule it (daily at 6am)
scriptmgr schedule add --type cron \
    --expr "0 6 * * *" --workflow 1

Execution Semantics

  • Parallel fan-out — nodes with no unsatisfied predecessors run concurrently in a thread pool.
  • Join — a node fires only when ALL of its predecessors are complete (implicit join: all).
  • Conditional edges — "on": "success" only fires if the source node exited 0; "on": "failure" fires on non-zero exit; "on": "always" fires regardless.
  • Retries — each node retries up to retry times before marking failure.
  • Parent run — each workflow execution has a parent Run record; each node execution is a child Run linked via parent_run_id.

Scheduling

APScheduler-powered triggers persisted to SQLite.

Trigger Types

Typeexpression formatExample
cron Standard 5-field cron: MIN HR DOM MON DOW "0 2 * * *" — 2am every day
interval Integer seconds "600" — every 10 minutes
date ISO 8601 datetime string "2026-06-01T09:00:00"
continuous Integer seconds delay after completion "10" — restart 10s after script finishes

Managing Schedules

# Add
scriptmgr schedule add --type cron --expr "0 */6 * * *" --script 2

# List
scriptmgr schedule list

# Pause / resume via API
PUT /api/schedules/{id}/disable
PUT /api/schedules/{id}/enable

# Delete
scriptmgr schedule delete 5

Persistence

Schedules are stored in the SQLite database via APScheduler's SQLAlchemyJobStore. They survive process restarts — when the API starts, all enabled schedules are automatically reloaded.

💡

Cron reference: MIN(0-59) HR(0-23) DOM(1-31) MON(1-12) DOW(0-6, 0=Sunday). Use * for "every". Example: "30 8 * * 1-5" = 8:30am Monday–Friday.

Reports & Logs

What's Captured Per Run

Log Retention

Log rows older than SCRIPTMGR_LOG_RETENTION_DAYS (default 30) are rotated to compressed files in data/logs/archive/. This prevents the SQLite DB from growing unboundedly on long-running systems.

💡

For very verbose scripts, configure a short timeout and redirect large outputs to a file — pass the output path as an arg or env var to your script, then register the output file as an artifact.

Notifications

Alerts on failure via email, Teams, and Slack.

When Alerts Fire

By default, a notification is dispatched when a run completes with status failed or timed_out. Successful runs do not send alerts (configurable).

Email (SMTP)

# .env
SCRIPTMGR_SMTP_HOST=smtp.yourcompany.com
SCRIPTMGR_SMTP_PORT=587
SCRIPTMGR_SMTP_USER=alerts@yourcompany.com
SCRIPTMGR_SMTP_PASSWORD=your-password
SCRIPTMGR_SMTP_FROM=scriptmgr@yourcompany.com

Email body includes: Run ID, script name, status, exit code, started/finished times, duration, and host.

Microsoft Teams

SCRIPTMGR_TEAMS_WEBHOOK=https://outlook.office.com/webhook/xxxx/IncomingWebhook/yyyy/zzzz

Messages use an Adaptive Card format (Teams v1.3) — no third-party SDK required, just a plain HTTPS POST.

To get the webhook URL: Teams → Channel → Connectors → Incoming Webhook → Create.

Slack

SCRIPTMGR_SLACK_WEBHOOK=https://hooks.slack.com/services/T.../B.../xxx

To get the webhook URL: api.slack.com/apps → Create App → Incoming Webhooks → Activate → Add New Webhook.

Notification Content

ScriptManager: fetch-data — Run #142 FAILED

Status:    failed
Exit code: 1
Duration:  47s
Host:      WIN-SERVER01
⚠️

Leave SMTP_HOST / TEAMS_WEBHOOK / SLACK_WEBHOOK blank to disable that channel. Notification failures are logged as warnings but do not affect the run status.

Main Windows Service

Run the entire ScriptManager orchestrator as a Windows service.

Overview

The scriptmgr service install command uses NSSM (Non-Sucking Service Manager) to install a Windows service named ScriptManager. This service:

  • Starts automatically on Windows boot
  • Hosts the FastAPI API server
  • Hosts APScheduler (all enabled schedules fire)
  • Starts a local Celery worker subprocess
  • Rotates logs to data\logs\service-stdout.log and service-stderr.log at 10 MB

Prerequisites

  • NSSM on PATH or set NSSM_PATH env var: nssm.cc
  • Redis running (as its own service — Memurai installs this automatically)
  • Run the install commands as Administrator

Install & Manage

# Install (run as Administrator)
scriptmgr service install

# Start
scriptmgr service start

# Stop
scriptmgr service stop

# Check status
scriptmgr service status

# Uninstall
scriptmgr service uninstall

Log Locations

FileContents
data\logs\service-stdout.logAPI + scheduler + worker stdout
data\logs\service-stderr.logErrors and tracebacks
💡

You can also manage the service via Windows Services (services.msc) or the NSSM GUI (nssm edit ScriptManager).

Always-On Script Services

Wrap any Python script as a supervised Windows service with heartbeat monitoring.

Use Case

Some scripts shouldn't be scheduled — they should always be running: file watchers, event listeners, polling loops, local AI inference servers. Wrap them as Windows services so they:

  • Start automatically on boot
  • Auto-restart if they crash (NSSM supervised)
  • Report a heartbeat to the ScriptManager dashboard every N seconds
  • Show "stale" status on the dashboard if the heartbeat stops

Generate & Install

# Generate the wrapper + installer, then install as Administrator
scriptmgr always-on install my-watcher \
    --script .\watchers\my_watcher.py \
    --interpreter python \
    --heartbeat 30 \
    --output-dir .\services

# This creates two files in .\services:
#   my-watcher_wrapper.py       ← restarts script + sends heartbeats
#   install_my-watcher.ps1      ← NSSM install script

# Run as Administrator to install:
pwsh .\services\install_my-watcher.ps1

What Gets Generated

Wrapper Script (my-watcher_wrapper.py)

"""Always-on wrapper — generated by ScriptManager"""
# Starts your script in a loop (restarts on failure)
# Sends heartbeat POST to /api/services/heartbeat every 30s
# Handles graceful shutdown signals

NSSM Installer (install_my-watcher.ps1)

# Registers the wrapper as a Windows service:
# - Service name: my-watcher
# - Auto-start on boot
# - Log rotation at 10 MB
# - Runs the wrapper with the configured Python interpreter

Monitoring in the Dashboard

After registering the script in ScriptManager, the always-on service section of the dashboard shows:

  • Service name & linked script
  • Current status (running, stopped, unknown, stale)
  • Last heartbeat timestamp
  • Process ID (PID)
💡

The always-on service must be registered in ScriptManager's DB (via scriptmgr script add) before the heartbeat endpoint recognises it. The service name must match exactly.

Scheduler Comparison

Best-in-breed evaluation for Python script scheduling.

Summary Decision

✅

Chosen: APScheduler + Celery. Pure-Python, embeds directly into FastAPI, persistent via SQLAlchemy, scales to remote workers via Redis. Zero extra infrastructure for scheduling metadata.

Options Evaluated

ToolVerdictReason
APScheduler + Celery ✅ Chosen Python-native, embeddable, cron/interval/date/custom triggers, SQLAlchemy jobstore, distributed via Redis
ArcanaDev JAMS Consider Later Commercial Windows-native enterprise scheduler. Excellent UI, SLA tracking, AD integration, audit. Revisit if you need enterprise compliance at 1000+ jobs.
Prefect 2/3 Runner-Up Modern Python orchestrator, first-class DAG support, great observability. Consider if DAG complexity grows significantly.
Apache Airflow Overkill Heavy: needs separate scheduler + web + workers + Postgres. Linux-leaning. Strong ecosystem but too much ops overhead here.
Dagster Overkill Asset-centric, great for data lineage. More opinionated than needed for general script ops.
Rundeck Wrong Stack JVM-based, good for ops teams. Not Python-native; adds a JVM dependency.
Windows Task Scheduler Too Limited No DAGs, no live logs, no API, weak grouping. Adequate for <10 standalone scripts, not for this use case.
Temporal / Cadence Overkill Durable workflow engines for long-running sagas. Powerful but heavy and complex to operate.
Quartz.NET Wrong Stack .NET ecosystem — doesn't apply here.

Migration Path

The ScriptManager data model is scheduler-agnostic. If you outgrow APScheduler:

  1. Export schedules and workflows from the SQLite DB.
  2. Swap src/scriptmgr/scheduler/apscheduler.py for a new adapter module (Prefect flows, JAMS jobs).
  3. The API, CLI, reports, and Windows service layers are unaffected.
