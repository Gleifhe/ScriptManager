Overview

ScriptManager is a local orchestration service running on your workstation. It lets you register, schedule, chain, and monitor scripts written in any language — all from a web browser.

ComponentWhat it does
Web UIThis browser interface — manage everything at http://localhost:8765
REST APIJSON API at http://localhost:8765/api — for automation or integration
SchedulerFires scripts on cron, interval, or continuous schedules automatically
RunnerLaunches your scripts as child processes, captures all output
DatabaseSQLite at data\scriptmgr.db — stores all config and run history
Windows ServiceKeeps everything running after reboot (set up via install-service.ps1)

Quick Start — 5 Steps

1 Go to Groups → click + New Group → enter a name (e.g. "AI Workflows") → Create
2 Go to Scripts → click + Add Script → fill in name, path, and select your group → Add Script
3 Click ▶ Run on your script — optionally add runtime parameters in the dialog → Run Now
4 You're taken to the Run detail page — watch live output as the script executes
5 (Optional) Go to Schedules to set it running automatically on a timer

1. Groups

Groups are folders that organise your scripts. Every script must belong to a group.

Creating a group

  1. Click Groups in the left sidebar
  2. Click + New Group
  3. Enter a Name (required) and optional description
  4. Click Create

Example groups

  • AI Workflows
  • Data Pipelines
  • Maintenance & Cleanup
  • Reports
  • DevOps
⚠ Deleting a group also deletes all scripts inside it and their run history.

2. Adding Scripts

A "script" is any executable file on disk — Python, PowerShell, Batch, Go, or a compiled binary.

Fields

FieldRequiredDescription
NameYesDisplay name — e.g. "Daily Report"
GroupYesWhich folder this script belongs to
Script / Executable pathYesFull path on disk — e.g. C:\scripts\report.py
Language / TypeNoLeave as Auto-detect — picks up from file extension. Override only if needed.
Default argsNoArguments always passed to the script. Supports quoted values: --env prod "my folder"
TimeoutNoKill script after N seconds. 0 = no limit.
DescriptionNoNotes shown in the scripts list

Path tips

  • Use the full absolute path: C:\Users\you\scripts\myscript.py
  • UNC paths work too: \\server\share\scripts\tool.exe
  • The script does not need to be inside the ScriptManager folder

Overriding the language

4. Running Scripts

Manual run

  1. Go to Scripts
  2. Click ▶ Run next to a script
  3. A dialog appears — optionally enter runtime parameters (extra args for this run only)
  4. Click Run Now — you're taken to the live log view

Runtime parameters

Parameters entered in the run dialog are appended to the script's default args:

Default args: --env prod
Runtime params: --output C:\results --date 2026-06-01
Final command: python script.py --env prod --output C:\results --date 2026-06-01

Use quotes for values with spaces: --folder "My Documents\Reports"

Run modes

ModeHow to use
One-shotClick ▶ Run — runs once and stops
ScheduledAdd a schedule (cron or interval) — runs automatically
Continuous re-runAdd a schedule with type continuous — re-runs automatically after finishing
Always-on serviceUse install-service.ps1 to wrap the whole server (or individual scripts) as Windows Services

5. Schedules

Schedules make scripts run automatically without any manual action.

Creating a schedule

  1. Go to Schedules → click + New Schedule
  2. Pick a Trigger Type and enter the Expression
  3. Select either a Script or Workflow to run
  4. Click Create

Trigger types & expressions

Managing schedules

  • Click ✓ On / ✗ Off to pause/resume a schedule without deleting it
  • Click Delete to remove it permanently

6. Workflows (Chaining Scripts)

Workflows let you chain multiple scripts together into a pipeline (DAG — Directed Acyclic Graph). Scripts can run sequentially, in parallel, or conditionally based on whether a previous step succeeded or failed.

Creating a workflow

  1. Go to Workflows → click + New Workflow
  2. Enter a name, optional description, and select a group → Create
  3. Click ✏ Build to open the visual workflow builder
  4. Add scripts from the right panel and connect them
  5. Click 💾 Save (or press Ctrl+S)

DAG structure

Script A → Script B → Script C    (sequential)
Script A → Script B                (parallel fan-out)
        → Script C
Script B + Script C → Script D   (join / merge)

Edge conditions

ConditionBadge colourMeaning
on success● greenOnly proceed if the previous script exited with code 0
on failure● redOnly proceed if the previous script failed (non-zero exit)
always● purpleAlways proceed regardless of exit code

Workflows can also be scheduled — add a schedule on the Schedules page and target the workflow instead of a single script. Workflow runs appear in Run History as a parent run containing all child step runs.

7. Visual Workflow Builder

The workflow builder is a visual, interactive editor for building multi-step pipelines without writing any JSON.

Opening the builder

Go to Workflows and click ✏ Build next to any workflow.

Adding steps

  • Use the Script Library panel (right side) — search for scripts by name or group
  • Click + on a script to append it to the pipeline, or drag it onto the canvas to insert at a specific position
  • Each step shows the script name, group, file path, and controls for retry and timeout

Configuring steps

FieldDescription
Condition badgeThe coloured pill between steps — click it to cycle: on success → always → on failure
RetryNumber of automatic retries if the step fails (0–5)
Timeout (s)Kill the step after N seconds. 0 = no limit.

Reordering steps

  • Or drag a step card to a new position

Saving

  • Click 💾 Save in the top-right
  • Press Ctrl+S at any time

  • The status indicator shows ✓ saved or ● unsaved changes

Running a workflow

Click ▶ Run Workflow in the builder header, or go to Workflows and click ▶ Run. You'll be taken to the live run detail page.

11. Always-On Services

Always-on services are scripts that should run continuously as Windows Services — automatically restarting on crash and surviving reboots. This is different from scheduled scripts: these are long-running daemons (watchers, listeners, agents).

Registering a service

  1. Go to 🔁 Always-On in the sidebar
  2. Click + Register Service
  3. Select the script and give it a Windows service name (e.g. MyWatcherSvc) → Register

Installing via NSSM

After registering, use the NSSM Command shown in the table to install the Windows service:

# Run as Administrator in PowerShell:
nssm install MyWatcherSvc "C:\scripts\my_watcher.py"
nssm set MyWatcherSvc AppRestartDelay 5000
nssm start MyWatcherSvc

Heartbeat monitoring

Your always-on script can call the ScriptManager API to report it's alive. Add this to your script's main loop:

import requests, time
while True:
    requests.post("http://localhost:8765/api/services/heartbeat",
        json={"service_name": "MyWatcherSvc", "status": "running"})
    time.sleep(60) # ping every 60 seconds
    # ... do your work

The Always-On page shows ● alive if the last heartbeat was within 2 minutes, or ● stale if overdue.

⚠ NSSM must be installed and on your PATH. Download from nssm.cc/download — place nssm.exe in C:\Windows\System32\ or any folder on PATH.

12. Notifications

ScriptManager can send alerts when a script fails, times out, or is cancelled. Notifications are configured via environment variables in the .env file in the project root.

Email (SMTP)

Add to .env:

SCRIPTMGR_SMTP_HOST=smtp.gmail.com
SCRIPTMGR_SMTP_PORT=587
SCRIPTMGR_SMTP_USER=you@gmail.com
SCRIPTMGR_SMTP_PASSWORD=your-app-password
SCRIPTMGR_SMTP_FROM=scriptmgr@yourdomain.com

Emails are sent to SCRIPTMGR_SMTP_USER by default. The subject line includes the script name, run ID, and status.

Microsoft Teams

SCRIPTMGR_TEAMS_WEBHOOK=https://outlook.office.com/webhook/...

Create a webhook in Teams: go to a channel → … → Connectors → Incoming Webhook.

Slack

SCRIPTMGR_SLACK_WEBHOOK=https://hooks.slack.com/services/...

Create a webhook in Slack: api.slack.com/messaging/webhooks.

✓ Notifications fire only on non-success runs (failed, timed_out, cancelled). Successful runs do not trigger alerts.
⚠ After editing .env, restart ScriptManager for the new settings to take effect: Restart-Service ScriptManager (as Administrator).

13. Windows Service (Auto-start on Boot)

ScriptManager itself is installed as a Windows Service called ScriptManager so it starts automatically when Windows boots — keeping the API, scheduler, and web UI always available.

Initial installation

Run this once in an Administrator PowerShell:

cd d:\repos\Test
.\install-service.ps1

Service management

ActionPowerShell commandRequires admin
Check statusGet-Service ScriptManagerNo
StopStop-Service ScriptManagerYes
StartStart-Service ScriptManagerYes
Restart (apply code changes).\restart-service.ps1Yes
View in GUIservices.mscNo

Development mode (no admin needed)

To test code changes without restarting the Windows Service, start a second server on a different port:

d:\repos\Test\.venv\Scripts\scriptmgr.exe serve --port 8766 --reload

Browse to http://localhost:8766 to test changes. The --reload flag auto-restarts when Python files change.

Service log files

  • d:\repos\Test\data\logs\service-stdout.log — normal output
  • d:\repos\Test\data\logs\service-stderr.log — errors / exceptions

Re-installing after a move

If you move the repo or update Python, re-run install-service.ps1 as Administrator to update the service paths.

14. REST API

ScriptManager has a full JSON REST API. All UI features are available via API too — useful for integrations, CI/CD pipelines, or calling from other scripts.

Interactive API docs

Open http://localhost:8765/docs — Swagger UI where you can explore and call every endpoint directly from the browser.

Key endpoints

MethodEndpointAction
GET/api/groupsList all groups
POST/api/groupsCreate a group
GET/api/scriptsList all scripts
POST/api/scriptsAdd a new script
POST/api/scripts/{id}/runRun a script (with optional params)
GET/api/runsList runs (filter: status, script_id, page)
GET/api/runs/{id}Get run detail
GET/api/runs/{id}/logsGet all log lines for a run
GET/api/schedulesList schedules
POST/api/schedulesCreate a schedule
GET/api/workflowsList workflows
POST/api/workflowsCreate a workflow
POST/api/services/heartbeatPost heartbeat from an always-on service
GET/_api/dashboardDashboard stats JSON (polled by the UI)

WebSocket — live log streaming

Connect to ws://localhost:8765/ws/runs/{run_id}/logs to receive log lines in real time while a run is active. Each message is a JSON object:

{"stream": "stdout", "line": "Processing row 1234..."}
{"stream": "stderr", "line": "Warning: file not found"}
{"stream": "system", "line": "__done__"} ← signals the run finished

Calling from another script

# Python — trigger a run and poll for completion
import requests, time

# Start the run
r = requests.post("http://localhost:8765/api/scripts/1/run",
    json={"params": ["--date", "2026-06-01"]})
run_id = r.json()["id"]

# Poll until done
while True:
    status = requests.get(f"http://localhost:8765/api/runs/{run_id}").json()["status"]
    if status in ("success", "failed", "timed_out", "cancelled"): break
    time.sleep(2)
print(f"Run finished: {status}")

15. Troubleshooting

ProblemFix
Site won't load at localhost:8765Run Start-Service ScriptManager (as Admin) or manually: d:\repos\Test\.venv\Scripts\scriptmgr.exe serve
Script shows "failed" with exit code 1Click Logs on the run — check stderr (red lines) for the actual error message
PowerShell script blockedThe runner uses -ExecutionPolicy Bypass automatically — if still blocked, verify the script path is correct and the file exists
Script not found / path errorUse a full absolute path in the script settings: C:\scripts\myscript.py. Relative paths are not supported.
Schedule not firingCheck the schedule is toggled On. Verify cron expression at crontab.guru. Restart ScriptManager to reload the scheduler.
Port 8765 already in useAnother instance is running. Stop it: Stop-Service ScriptManager (Admin) then start again.
Service won't start after rebootCheck data\logs\service-stderr.log for errors. Re-run install-service.ps1 as Administrator.
Database errors / missing tablesRun d:\repos\Test\.venv\Scripts\scriptmgr.exe db init to re-initialise the database.
Code changes not appearingThe Windows Service must be restarted to pick up code changes: run .\restart-service.ps1 as Administrator, or test on port 8766 dev server.
Notifications not sendingCheck .env has the right SMTP/webhook settings. Restart the service after changes. Check service-stderr.log for auth errors.
Dashboard not auto-refreshingClick ▶ Resume on the dashboard — refresh may have been paused. Check browser console for network errors.
Workflow run shows no step detailsOpen the parent run in Runs — child step runs are linked via parent_run_id and visible via the API at /api/runs?parent_id={id}.

Log files

  • Service output: d:\repos\Test\data\logs\service-stdout.log
  • Service errors: d:\repos\Test\data\logs\service-stderr.log
  • Run logs: stored in the database, viewable on each run's detail page or via /api/runs/{id}/logs
